# iOS Deployment Readiness

## Context

Destiny's `ios/` native project exists and has CocoaPods installed, but it was last prebuilt before `expo-image-picker` was added and before `react-native-google-mobile-ads` was wired into `app.config.js` — so its native `Info.plist` is missing permission strings those features need, its `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` are stuck at the very first prebuild's `1.0.0`/`1` (vs. `app.json`'s current `2.3.0`), and no Apple signing identity has ever been configured on this Mac (confirmed: `security find-identity -v -p codesigning` → 0 identities, no provisioning profiles directory). The user hasn't enrolled in the Apple Developer Program yet, so this plan does everything that's possible without that account now, and leaves a precise, ordered checklist for what only the user can do once they enroll. Per the user's choice, the release pipeline mirrors Android's existing pattern (raw Xcode build via GitHub Actions), not EAS Build.

## What I can do now

### 1. Close the Info.plist permission gaps via `app.json`

- Add `expo-image-picker` to the `plugins` array with a `photosPermission` string (same pattern as the existing `expo-camera` entry), so gallery-upload QR joining gets its `NSPhotoLibraryUsageDescription`.
- Remove the redundant, differently-worded `NSLocationWhenInUseUsageDescription` currently hand-set in `app.json`'s top-level `infoPlist` — the `expo-location` plugin already generates the canonical (and more complete) foreground+background strings; having both is just a source of drift (confirmed the two already read differently).
- `react-native-google-mobile-ads`'s plugin (already wired via `app.config.js`) will inject `GADApplicationIdentifier`, `SKAdNetworkItems`, and `NSUserTrackingUsageDescription` automatically once prebuild runs — no manual config needed for that.

### 2. Sync version/build number

Add `"buildNumber": "12"` to `app.json`'s `ios` block (matching Android's current `versionCode: 12`, and the same convention going forward: bump both together). This is what lets prebuild correct the stale native `1.0.0`/`1`.

### 3. Run `npx expo prebuild --platform ios` to apply all of the above

This requires `GoogleService-Info.plist` to exist at the repo root first (Firebase's config plugin does a hard file copy and throws otherwise — confirmed this exact failure earlier). Since the user doesn't have the real one yet (needs Firebase Console access to register the iOS app and download it — outside what I can do), **I'll create a syntactically-valid placeholder `GoogleService-Info.plist`** (fake but correctly-shaped values) solely to unblock running prebuild and a compile-only verification build. It's already `.gitignore`'d so this is safe and won't get committed. This must be replaced with the real downloaded file before the app will actually run/authenticate — flagged clearly in the checklist below.

### 4. Flatten the App Store icon

`assets/icon.png` is already 1024×1024 (correct size) but has an alpha channel, which App Store Connect rejects. I'll generate `assets/icon-ios.png` (alpha flattened onto an opaque background via Python/Pillow, already available in this environment from earlier session work) and point `app.json`'s `ios.icon` at it — leaving the shared `icon.png` (used by Android) untouched.

### 5. Scaffold `.github/workflows/ios-build.yml`

Mirrors `android-build.yml`'s structure and secret-injection pattern (`.env` written line-by-line from the same `EXPO_PUBLIC_FIREBASE_*` secrets, plus `EXPO_PUBLIC_ADMOB_IOS_APP_ID`/`EXPO_PUBLIC_ADMOB_BANNER_UNIT_ID_IOS` instead of the Android Maps key) but on `macos-latest`, with `pod install`, then an archive+export step gated on four new secrets that don't exist yet: `IOS_DIST_CERTIFICATE_BASE64`, `IOS_DIST_CERTIFICATE_PASSWORD`, `IOS_PROVISIONING_PROFILE_BASE64`, `APPLE_TEAM_ID`. Exactly like `android-build.yml` needing `KEYSTORE_BASE64` etc. today, this workflow will exist and be correct but non-functional until those secrets are added — that's expected and matches the existing Android precedent.

### 6. Update `README.md`

Add an iOS-parallel set of steps next to the existing Android ones in "One-time setup": registering the iOS app in Firebase Console, downloading the real `GoogleService-Info.plist` to the project root, Apple Developer Program enrollment, and Xcode signing-team setup. Also document the new CI secrets alongside the existing Android ones.

## What only the user can do (in order)

1. **Enroll in the Apple Developer Program** ($99/yr, developer.apple.com) — hard blocker for everything past simulator builds.
2. Sign into that Apple ID in Xcode (Xcode → Settings → Accounts).
3. **Register the iOS app in Firebase Console** (bundle ID `com.vinodsigadana.destiny`) and download the real `GoogleService-Info.plist`, replacing the placeholder at the project root.
4. In Xcode, open `ios/Destiny.xcworkspace`, select your Team under Signing & Capabilities for the `Destiny` target (Debug and Release), and let Xcode provision it. Also add the **App Attest** capability there (needed for Firebase App Check on iOS — can't be pre-configured without a Team selected).
5. Register the App ID + create an app record in **App Store Connect**, fill in metadata, screenshots, age rating, and the privacy nutrition label (referencing `docs/PRIVACY_POLICY.md`), and set up TestFlight.
6. Create a real AdMob iOS app + banner ad unit (same process already done for Android) and set `EXPO_PUBLIC_ADMOB_IOS_APP_ID` / `EXPO_PUBLIC_ADMOB_BANNER_UNIT_ID_IOS` in `.env`.
7. Once you have a distribution certificate (`.p12`) and provisioning profile, add the 4 GitHub Actions secrets named above so `ios-build.yml` can produce signed IPAs.

Note: this app currently only uses **local** notifications (the persistent "journey in progress" notice and arrival alerts), not remote push — so no APNs key / `aps-environment` entitlement is needed for what exists today.
